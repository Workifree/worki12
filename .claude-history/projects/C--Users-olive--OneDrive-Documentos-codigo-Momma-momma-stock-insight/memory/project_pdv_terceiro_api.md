O PDV de terceiros é o **Pedido Certo** (`pedidocerto.digital`), usado em 2 unidades: **Momma Asa Sul (306)** e **Momma Lago Sul (SIX)** → nossos `loja_id` 2 e 4 (confirmar nomes). Integração **bidirecional**: (A) Pedido Certo chama NOSSA API `pdv-movimentacao`; (B) NÓS consumimos a API read-only deles (`https://pedidocerto.digital/api/v1`, `Authorization: Bearer pc_live_sk_...`, escopo por loja) + webhook `order.paid` (HMAC, tempo real) — direção B é **fase posterior** (decisão Giovanni). **Segredos do Pedido Certo (live keys + senha admin) NÃO ficam no repo** — guardar como secrets Supabase/1Password (sugestão: `PEDIDO_CERTO_API_KEY_ASA_SUL/_LAGO_SUL`, `PEDIDO_CERTO_WEBHOOK_HMAC_SECRET`). Onboarding (texto de handoff p/ o parceiro) em `docs/pdv-movimentacao/ONBOARDING-parceiro.md`. Auth da NOSSA API vai aceitar `Authorization: Bearer` (simetria) + `x-api-key`.

API HTTP `pdv-integracao` (renomeada de `pdv-movimentacao` em 2026-06-30; edge function Supabase, `verify_jwt=false` + auth própria por API key) para o Pedido Certo replicar o **scanner de contagem**: lê nosso QR de caixa e registra **entrada/saída** de movimentação no nosso ERP. A caixa **se movimenta** entre lojas (entrada credita, saída debita o nosso estoque) — **não há consumo de caixa** por aqui (consumo = diminuir itens, outro fluxo). Lotes/etiquetas continuam **gerados por nós na fábrica**; o PDV só consulta e movimenta. **3ª capacidade (implementada+revisada): `POST /requisicao`** (migration 20260625150000 + RPC `criar_requisicao_pdv`) — o sistema deles gera pedido de itens p/ a loja que cai na aba Logística como card do dia. Itens por `produto_master_id` (nome canônico de `produtos_master`; id inativo/inexistente → 422 `itens_invalidos` atômico). Idempotência por `(pdv_api_key_id, pedido_externo_id)`. Auth aceita `Authorization: Bearer` + `x-api-key`. Erros mapeados por campo `codigo`. Doc `API.md` cobre os 4 endpoints (v1.1). Card aparece só com `status='em_fila'` (literal), `loja_solicitante`=nome textual, `data_recebimento` ISO (hoje-14..hoje+27), ≥1 item (`quantidade_solicitada>0`, `nome_produto` único). `/logistica` (Logistica.page.tsx, fetchQueue) NÃO é realtime — operador recarrega; ao-vivo exigiria subscription nova (UI/Gemini).

**Endpoints:** `GET /etiqueta/:uid` (estado + timeline + vencido), `POST /entrada`, `POST /saida` (batch de UIDs), `POST /requisicao` (cria card na Logística).
**Auth:** tabela `pdv_api_keys` (hash bcrypt, escopo `loja_ids int[]`, revogável). Provisionar via RPC `criar_pdv_api_key(nome, loja_ids)` (gate `admin/master`, chave em claro UMA vez). Revogar: `revogar_pdv_api_key`. Validar: `validar_pdv_api_key` (service_role, timing-safe).
**RPCs de movimento:** `movimentar_etiqueta_pdv` (unitária) / `movimentar_lote_pdv` (batch). Reusam `bipar_etiqueta` (idempotência por máquina de estados — NÃO índice único; ciclo entra↔sai repete). Motivos `entrada_pdv_externo`/`saida_pdv_externo` na whitelist do trigger `tg_movimentacoes_sync_estoque_lotes`. Responsável = usuário-sistema `usuarios.username='pdv_integracao_sistema'` (sem auth.uid). Ordem correta multi-loja: **saída@origem → entrada@destino** (senão alerta "sem saída registrada", não bloqueia). Lote vencido = alerta, não bloqueia.
